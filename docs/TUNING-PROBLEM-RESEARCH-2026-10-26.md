# Tuning problems → DD84 implementation

Research date: October 26, 2026. Owner requested broad research into tuner, shop and customer problems and practical implementation in DD84.

This is a qualitative, public-source survey. It does not measure prevalence or cover every forum, vehicle or controller. Older threads reveal workflow problems, not current software instructions. Search-index excerpts and inaccessible pages are identified separately. No forum attachments, tune maps, customer logs, proprietary definitions or long copied passages were imported. Forum opinions do not establish a diagnosis or calibration target.

## Findings and implemented responses

| Wideband / trim disagreement | [HP Tuners transform documentation](https://docs.hptuners.com/VCM_Scanner/Channels/Transforming_A_Channel/) establishes the external-signal conversion workflow. | Wideband checklist records input type, scaling and AFR/lambda basis. It requests evidence before suggesting an airflow investigation; it generates no correction percentage. |

It stays local until the operator chooses to share the JSON. |
| Revision names mistaken for evidence | [VCM Editor guide](https://files.hptuners.com/help/VCMEditorUserGuide.pdf), tune-history sections, describes revision comparison. | Intake distinguishes operator-confirmed tune/log association from unknown/mismatch. Existing DD84 source fingerprints and before/after reviews remain separate evidence. Missing after-data cannot establish improvement. |

## Coverage and access limitations

Public first-person discussions were reviewed through retrieved pages or indexed text from HP Academy, LS1Tech, Link ECU, NASIOC, EFILive and the rusEFI issue tracker. These are examples, not a statistical sample. Reddit HPtuners/ECU_Tuning/HolleyEFI/WRX discussions were searched for leads; unsupported advice and promotion were not used as technical authority.

HP Tuners forum searches returned relevant indexed reports, including [wideband connectivity](https://forum.hptuners.com/showthread.php?100079-Wideband-Connectivity-issue-resolved=) and [read errors](https://forum.hptuners.com/showthread.php?114321-Failed-to-retrieve-Flash-Data-on-initial-read-unlock=). Direct retrieval returned no-thread/robots restrictions; manufacturer documentation supports the implemented checks instead. The [Holley troubleshooting checklist](https://forums.holley.com/forum/holley-efi/holley-efi-aa/932-troubleshooting-checklist-holley-efi) was indexed but direct retrieval returned 403; its contents were not treated as verified instructions. A [MSEXTRA cranking-sync thread](https://www.msextra.com/~msextra/forums/viewtopic.php?p=598539) returned a server error. No access restrictions were bypassed.

Additional searches covered RomRaider and Speeduino. The retrieved [Speeduino trigger manual](https://wiki.speeduino.com/en/configuration/Trigger_Setup) reinforces the need for controller-specific setup. The RomRaider query did not yield an adequate reviewed source in this pass. These searches do not establish native DD84 compatibility. Transmission, diesel-specific control, hybrid/EV and further OEM ecosystems require focused research and verified definitions before implementation beyond the general intake workflow.

## Implementation boundaries and acceptance

The shared `troubleshooting.mjs` catalog drives both the web `/troubleshoot` page and Windows Studio's Troubleshooting workspace. Ten symptom/workflow categories share operator-entered context and explicit unchecked/checked/concern/not-applicable states. Every checked or skipped item needs evidence or an explanation. Unknown association, mismatched files and recorded concerns cannot silently become a completed handoff. Even the most complete case is only **ready for human review**.

`DD84_TROUBLESHOOTING_CASE_V1` records reopen in both interfaces. Imported assessments and source URLs are discarded and reconstructed from the bundled catalog. Unsupported schemas, oversized files, invalid statuses and unknown check keys are rejected before replacing the current record. Unsaved replacement uses an inline choice; navigation preserves state. This is not an automatic fault detector, a learned model, a tune map, a source-file backup or an ECU release gate.

The same pass repairs customer-workflow gaps found in the code: existing uploaded files can be selected again; job switching clears file selections; requests show pending/error/retry states; latest analysis status can be recovered after reopening a job. Backend ownership and exact job membership are checked before creating an analysis run. The existing human-release and simulation-only gates remain unchanged.

Next priorities, after real operator feedback: connect these cases to authenticated jobs with explicit sharing; measure repeat requests caused by missing evidence; expand log formats only with validated parsers; add controller-specific diagnostic rules with test fixtures and provenance. Track intake completeness and reviewer usefulness, not an unvalidated claim of engine improvement. No background forum scraping or monitoring is configured.
